# 面試任務說明 (Interview Task)

歡迎，也謝謝你撥時間參與。請先完整讀完本頁再開始。

---

## 情境

你今天加入了一個既有專案 **ShiftForge**（排班自動化生成模組）。

前一位負責的同事已經離職。他在離開前重構了資格檢查與規則設定，
之後**專案就無法正常產出班表了**。沒有人留下交接文件，只有一份模組規格書（Wiki）
還算完整。

你的任務是：**讓這個專案重新符合規格書的描述。**

---

## 時間與工具

| 項目 | 說明 |
| :-- | :-- |
| 預期投入 | **3–4 小時** |
| 交件期限 | 收到題目後**一週內** |
| 工時回報 | **必填**——請在 PR 描述中誠實回報你實際花了多久 |
| AI 工具 | **可以自由使用**（Claude、Copilot、ChatGPT 等），不需迴避，也不用特別聲明 |
| 網路 | 可以查詢任何資料 |

> 期限是一週，但**預期投入是 3–4 小時**。期限只是讓你自己安排時間，不是建議你花一週。
>
> 我們知道你會用 AI，這正是我們日常工作的方式。
> 我們想看的不是「你能不能自己寫出來」，而是**你怎麼判斷 AI 給的東西對不對**。

---

## 你要做的事

1. 用我們寄給你的 **git bundle** 還原專案：

   ```bash
   git clone shiftforge.bundle shiftforge
   cd shiftforge
   ```

2. 推到**你自己的 GitHub repo**（public 或 private 皆可，private 請加我們為協作者）。
3. 從 `main` 開一個修復分支（分支名稱自訂）。
4. 讓專案符合[模組規格書](Module-Specification.md)的描述。
5. 在**你自己的 repo 內**開一個 Pull Request（修復分支 → `main`），交件時把連結給我們。

### 環境

```bash
uv sync
uv run shiftforge examples/clinic_week.json
```

需要 Python 3.11+ 與 [uv](https://docs.astral.sh/uv/)。

---

## 判準

### 及格線

以下三個範例都必須能正常執行並收斂：

```bash
uv run shiftforge examples/clinic_week.json
uv run shiftforge examples/ward_tight.json
uv run shiftforge examples/pharmacy_relief.json
```

三個都應該：離開碼為 `0`、`converged : True`、`hard violations: 0`。

並且 `uv run ruff check src` 與 `uv run ruff format --check src` 通過。

### 但這只是及格線，不是滿分

**「程式沒報錯」不等於「符合規格」。**

這個專案裡**有些問題不會讓任何一個範例失敗**。三個指令全部變綠，不代表你已經做完了。

加分項：

- 找到出的範例**照不到**的問題
- 對規格書未明確定義之處，說明你的**兩種理解**分別是什麼、你選了哪一個、為什麼
- 補上能證明你的修正正確的**測試**

---

## 重要：沒有標準答案檔

本題**刻意不提供**預期輸出檔（golden file），也**沒有現成的測試**會告訴你答案。

**唯一的正確性判準是[模組規格書](Module-Specification.md)。**

這代表：

- 你需要自己想辦法確認你的修正是對的。
- **如何驗證**，本身就是這題要看的能力之一。
- 光是「三個範例通過」不足以作為「我做對了」的證據——請想想還能用什麼方式增加你的把握。

> 提示：規格書與[設定檔 Schema](Configuration-Schema.md) 對每個範例的性質都有文字描述。
> 那些描述是規格的一部分，值得仔細對照。

---

## 遇到規格沒寫清楚的地方

規格書不見得涵蓋所有情況。如果你遇到**規格沒有明確定義**的地方：

**請在 PR 描述中明確寫下來**，包含：

- 你確認過規格書真的沒寫（而不是你沒讀到）
- 你的**兩種理解**分別是什麼
- 你**選了哪一個**，以及為什麼

> 自己憑空假設一個答案然後**默默做下去**，是我們**最不希望**看到的處理方式。
> 把模糊處攤開來講，即使你的選擇跟我們想的不一樣，也是加分。

---

## 我們會看什麼

| 面向 | 我們在意的事 |
| :-- | :-- |
| **問題拆解** | 你怎麼從「壞掉了」定位到「哪裡壞了」？先做什麼、後做什麼？ |
| **跨模組理解** | 問題不一定在報錯的那一行。設定檔、驗證器、策略、決策迴圈之間的關係，你有沒有看懂？ |
| **驗證方法** | 在沒有標準答案的情況下，你怎麼說服自己（和我們）你的修正是對的 |
| **判斷力** | 你有沒有盲目接受 AI 的建議？有沒有發現規格與程式碼衝突的地方？ |
| **Git 操作** | commit 的粒度是否合理、訊息是否說得清楚、有沒有把不相關的改動混在一起 |
| **溝通** | PR 描述能不能讓 reviewer 不看程式碼就知道你改了什麼、為什麼、以及你卡在哪 |

### 我們**不**在意的事

- 你用了哪個 AI 工具、用了多少
- 程式碼風格是否華麗——能運作、能讀懂就好
- 你有沒有把所有問題都解決——**誠實說明你卡在哪，比假裝沒事更有價值**

---

## 二面

二面時我們會請你**講解你自己的修改**。

請確保你能說明：**你改了什麼、為什麼那樣改會有效。**

不需要知道專有名詞——能講清楚機制就可以。但如果你交出來的改動自己解釋不了，
那對我們來說跟沒做是一樣的。

## 提交前的檢查清單

- [ ] 三個範例都能執行，離開碼為 `0`
- [ ] `uv run ruff check src` 通過
- [ ] `uv run ruff format --check src` 通過（若未過可先執行 `uv run ruff format src` 自動修正）
- [ ] commit 訊息說得清楚（格式建議：`[Type] Message`，Type 可用
      `Update` / `Fix` / `Config` / `Test` / `Doc` / `Refactor`）
- [ ] PR 描述包含：**你發現了什麼問題**、**為什麼會這樣**、**你怎麼確認修好了**
- [ ] PR 描述包含：**你實際花費的時間**
- [ ] PR 描述包含：**規格模糊處**與你的選擇（若有）
- [ ] 如果有沒解決的部分，在 PR 中明確說明

## 常見問題

**Q：我可以修改規格書嗎？**
A：不行。規格書是判準，不是待修的程式碼。但如果你認為規格書本身有錯或不清楚，
請在 PR 描述中說明——**這會加分**。

**Q：我可以修改 `examples/` 底下的範例嗎？**
A：不建議。範例代表使用者的真實需求。如果你認為某個範例本身不合理，
請在 PR 中說明理由，不要直接改掉它。

**Q：我可以新增範例或測試嗎？**
A：非常歡迎。新增（而非修改）範例來驗證你的修正，以及補上測試，都是明顯的加分。

**Q：我需要修好全部的問題嗎？**
A：盡力就好。修好一部分並且清楚說明剩下的狀況，比宣稱全部修好但實際沒有更好。

**Q：`soft violations` 不是 0，是我改壞了嗎？**
A：不一定——軟規則不阻擋交付，規格書有定義 `hard` 與 `soft` 的差別。
但這**不代表你可以忽略軟規則層**：請確認它的行為確實符合規格書與設定檔的描述。

**Q：預期投入 3–4 小時，我超過了怎麼辦？**
A：沒關係，誠實回報就好。我們看的是你怎麼做，不是你多快做完。
但如果你發現自己遠超過這個數字，請先交出目前的成果並說明卡在哪，不要無限期地做下去。
